# Раздельные хранилища пользователей

## Изменения

У каждой записи профиля, документа, карты, пароля, ключа и клада теперь есть обязательный владелец. Сервер берёт его из авторизованного сеанса. Списки, счётчики, поиск, чтение по ID, изменения, удаление и вложения ограничены этим владельцем. Даже мастер не получает доступ к чужим записям через обычные API хранилища. «Общие» пароли означают общие для профилей внутри собственного хранилища, а не доступные другим аккаунтам.

Физически PostgreSQL остаётся общей БД; изоляция реализована на сервере по владельцу каждой записи. Это не отдельное шифрование с личным ключом пользователя и не защита от администратора самого сервера.

Мастер может изменить имя участника и сбросить его пароль, а также удалить участника вместе с его записями, вложениями, настройками и сеансами. Удаление требует явного подтверждения в интерфейсе. Мастер не может удалить себя или изменить собственную роль через этот экран. Смена пароля завершает все сеансы изменённого аккаунта. При выборе пароля проверяется, что он не используется другим аккаунтом, поскольку вход остаётся без логина.

PIN и локальные заметки разделены по аккаунтам. Старый общий PIN и заметки в браузере наследует только мастер. При смене пользователя очищаются данные запросов и состояние чувствительных экранов. Вход в другой аккаунт в соседней вкладке закрывает старое хранилище. API проверяет идентификатор аккаунта вкладки против cookie сеанса. Ответы и вложения больше не кешируются браузером (`Cache-Control: no-store`).

Из пользовательского API ключей убрано поле `file_path`, через которое раньше можно было подставить произвольный путь к файлу. Путь задаёт только сервер при загрузке.

Поле даты на iPhone ограничено шириной формы; подправлены ширина поиска в шапке и размер галочки совпадения адресов.

## Обновление существующей установки

Новая миграция: **`a7b8c9d0e1f2`**. По решению владельца проекта все прежние записи передаются единственному мастеру; существующие участники получают пустые хранилища. Это включает записи, которые могли быть созданы участниками до разделения: раньше авторство не сохранялось.

Миграция добавляет владельца и индексы, сохраняет содержимое записей и пути вложений, завершает старые сеансы. Если в непустой базе нет ровно одного мастера, она останавливается без выбора случайного владельца. Обратная миграция запрещена: удаление признака владельца смешало бы личные хранилища. Откат — восстановление резервной копии вместе с предыдущей версией приложения.

1. Сделать резервную копию PostgreSQL и каталога вложений.
2. Обновить код и остановить backend на время миграции.
3. Выполнить `alembic upgrade head` в окружении backend. Для Docker при остановленном backend: `docker compose run --rm backend alembic upgrade head` (образ backend должен быть пересобран).
4. В `frontend`: `npm ci` и `npm run build`; опубликовать новую папку `dist`, затем запустить backend.
5. На устройствах перезагрузить приложение и войти заново. Войти мастером, проверить прежние данные; войти участником — хранилище должно быть пустым. Затем проверить создание собственных записей, изменение имени/пароля и удаление тестового участника.

Для существующего Windows desktop применяется та же передача владельцу при запуске. В SQLite старые таблицы не пересоздаются, чтобы не вызвать каскадное удаление дочерних записей; обязательность нового поля обеспечивают триггеры, связь с пользователем — внешний ключ.

## Проверка

Итоговый локальный прогон: 27 backend-тестов и 36 браузерных тестов прошли. Production-сборка frontend и ESLint изменённых файлов проходят. Остаются прежнее предупреждение сборки о размере основного JS-файла и прежние lint-ошибки в незатронутых компонентах.

Backend-тесты проверяют изоляцию в обе стороны между мастером и участниками, доступ по известным чужим ID, поиск, привязку к профилям, чтение и изменение файлов, права управления пользователями, смену паролей и отзыв сеансов. Тесты миграции проверяют сохранность старых данных и дочерних записей, повторный запуск и остановку при неоднозначном владельце.

Браузерные тесты Chromium/WebKit проверяют мобильную форму, управление пользователями, подтверждение удаления, переключение аккаунтов, отдельные PIN/заметки и прежние сценарии блокировки и карт. Системный снимок iOS этими тестами не проверяется.

Проверки БД выполнены на SQLite с включёнными внешними ключами. Дополнительный прогон на настоящем PostgreSQL локально не выполнен: Docker Engine недоступен. Перед обновлением рабочей базы нужна её резервная копия; желательно сначала применить миграцию на копии PostgreSQL.

## Снимок в переключателе iOS

Проверка владельца на настоящем iPhone подтвердила: системный снимок может опередить веб-обработчик и показать интерфейс. Эта проблема **не решена в PWA**. Текущая блокировка защищает возврат в приложение, но не гарантирует безопасный снимок. Для контроля снимка нужен нативный iOS-контейнер с защитой на уровне жизненного цикла приложения и отдельная проверка на устройстве. Дополнительные таймеры в JavaScript такой гарантии не дают.
